# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Discord moderation system in two parts:

1. **`mai/`**: Node.js 24 ESM app (discord.js + express + discord-interactions + pino + yaml). Runs two Discord connections side by side: an HTTP interactions endpoint (`POST /interactions`, slash commands, autocomplete, buttons, modal submits, reached through cloudflared) and an outbound gateway WebSocket (`messageCreate`, `messageUpdate`, `messageDelete`, `guildMemberAdd`). Moderation and chat run in-process: OpenAI-compatible HTTP calls for classification and replies, SQLite (`node:sqlite`) for state, and an interval timer that enforces the grace period. The bot has a persona: **Mai**, the server's cat: mention/reply/DM chat, keyword emoji reactions, optional welcome messages, custom presence. Everything she says lives in `mai/config/mai.yaml`.
2. **`docker-compose.yml`**: stack of `mai` + `cloudflared` on the `edge` network, plus the `mai-data` volume for the database.

Full details: [README.md](README.md), [mai/README.md](mai/README.md), [COMMANDS.md](COMMANDS.md) (every command and right-click action, option by option).

## Commands

```sh
docker compose up -d --build mai   # rebuild + restart bot after code changes
docker compose logs -f mai         # structured pino JSON logs
docker compose run --rm mai npm run register   # sync slash commands with Discord
npm test                           # (in mai/) node:test, no deps, no network
```

- **`.env` changes require container recreate** (`docker compose up -d mai`). A plain restart does not re-read the env file, this has caused real debugging sessions.
- `.env` holds all secrets (gitignored); `.env.example` is the documented template. Env config is read and validated once in `mai/src/config.js`: add new env vars there, not via scattered `process.env` reads.

## Writing rules

- **Never use an em-dash (`—`).** Not in code, not in comments, not in anything Mai says, not in the YAML content file, not in documentation, not in commit messages. Use a colon when the second half explains the first, a semicolon or a full stop when it is a separate thought, parentheses for an aside, or restructure the sentence. This applies to everything written from now on; existing text is not rewritten just to satisfy it, but any line you touch for another reason should come out without one.

## Architecture constraints that aren't obvious from single files

- **Two config surfaces, both loaded once at startup**: `src/config.js` = operational (secrets, models, flags, timings, limits) from the environment; `src/content.js` = everything user-facing, loaded and validated from `mai/config/mai.yaml` (`MAI_CONFIG_PATH`). No handler may contain a literal string Mai says: persona, prompt scaffolding, scold lines, warning-DM template, `/mai` replies, welcome lines, reaction regexes and presence statuses all live in the YAML. Adding wording = YAML key + a validated field in `content.js`.
- **A knob needs a reason to exist, and there are three tiers**: an environment variable is justified by a secret, a fact about the deployment (port, path, ids) or a policy that differs per server. Everything else is a **constant in `config.js`** (the enforcer interval, the per-tick row cap, the interactions body cap, chat history turns, vision image count, reply length cap, the wedged-loop threshold), because fifty variables an operator has to form an opinion about is the reason the file was hard to approach. Between the two sits a tier that still reads the environment but is **absent from `.env.example` and the README**: the timings the test suite varies (`OPENAI_MAX_RETRIES`, `OPENAI_TIMEOUT_MS`, the four rate-limit knobs, `MODERATION_MAX_ROWS_PER_TICK`, `MODERATION_DEGRADED_AFTER`, `PRESENCE_ROTATE_HOURS`). The environment is already the seam the tests use, and a test-only setter exported from production code would be worse: reachable, not offered. Turning a variable into a constant means a `deprecate()` entry too, or a deployment's carefully chosen number silently stops being read.
- **Interactions vs. gateway split**: everything from Discord's HTTP side (commands, autocomplete, buttons, modals) is signature-verified by `verifyKeyMiddleware`: no `express.json()` may run before it on that route, though `limitRate` and `limitBody` deliberately do: the endpoint is public through the tunnel and the signature check is the expensive part, so a flood has to be turned away *in front of* it. The rate limiter keys on `CF-Connecting-IP` (every request otherwise carries the cloudflared container's IP) and logs refusals at `debug`, because at HTTP volume an `info` line per refusal turns a flood into a second flood in the log. Verified requests are then dispatched by `src/interactions/router.js`, which is also where the guild allowlist and the kill switch are enforced, for **every** interaction kind including autocomplete. `refusalReason()` decides; each router answers in its own protocol, because they cannot all refuse the same way: an autocomplete has to be refused with an empty choice list, and answering one with a message is a protocol error Discord rejects rather than a refusal anyone sees. `http/server.js` stays a thin transport. Message events only exist on the gateway (handler in `src/gateway/events/` + `client.on()` in `src/gateway/client.js`).
- **Interaction deadline and deferral**: Discord needs the HTTP response in ~3 s. A handler that cannot make it declares `deferred` (boolean or `(interaction) => boolean`); the router sends a placeholder, then edits it via the interaction webhook (`editOriginalResponse`) when the handler resolves. Two traps: `ephemeral` is fixed at defer time and the later edit **cannot** change it (`toMessageBody` strips `flags`), so a deferred public command must return public refusals too; and the interaction token expires after 15 minutes, so a failed edit is not retried. `send` is called exactly once per interaction. New slash command = file in `src/commands/` + entry in `src/commands/index.js` + `npm run register`. New button/select/modal = handler map exported from the feature module + entry in `src/interactions/registry.js`.
- **Read command options through `src/interactions/options.js`**: `resolveSubcommand(interaction)` flattens plain subcommands *and* subcommand groups into `{ group, name, options }`, so `/mod config set` and `/mod status` are handled the same way; `optionValue(options, name)` reads a single option. Handlers must not walk `interaction.data.options` themselves: the shape differs between the two cases. This module is deliberately separate from `router.js` to avoid an import cycle (router → command registry → commands).
- **Component state lives in the `custom_id`** (`name:arg:arg`, split by `parseCustomId`): there is no server-side interaction session. **An id from the client names a target, it never authorizes one.** A handler acting on behalf of a user must verify the id belongs to the clicker (`forgetComponents`), and a handler acting on a *channel or message* must verify it belongs to the clicker's guild (`report-approve` checks `channel.guildId === interaction.guild_id` before deleting, because the bot's client can reach every guild Mai is in). An ephemeral message is not an authorization boundary either. When such a check fails inside a handler that is deferred, it must **not** answer with a refusal (after a defer the response replaces the log entry); it falls through as a failed action so the outcome lands in the entry instead.
- **Two authority tiers, and they are not the same**: Manage Messages makes someone staff *in one guild*; `OPERATOR_USER_IDS` (`isOperator()` in `config.js`) is whoever runs the process. Mai serves several guilds from one database, so every counter a command prints has to be scoped: `depth`, `history.stats`, `usage.totalsFor` and `usage.breakdownFor` all take an optional `guildId` and `/mod` passes `visibleScope(interaction)`: the calling guild unless the caller is an operator. The same border applies to *acting*: `forgiveUser(guildId, userId)` is guild-scoped because a pardon is an exercise of authority. The deliberate exception is `openViolations(userId)`, which stays cross-guild: Mai having one memory of a member is not the same as one guild's staff reaching into another.
- **Code reached from the HTTP side has no gateway client of its own**: use `getGatewayClient()` from `src/gateway/client.js`, which is null until the gateway is ready. Slow Discord REST work triggered by a command runs detached (see `undoFlagMarks` in `src/commands/mod.js`).
- **Settings resolve through three layers, and `.env` is not one of them**: explicit override (`guild_settings` column, NULL = not set) > the guild's `profile` (a *name*, resolved live against `PRESETS`) > `BASE_SETTINGS` in `src/moderation/presets.js`. `effectiveSettings(guildId)` in `src/db/settings.js` is the single merge point, and it returns `inherited` (did this server set the key itself?) plus `source` (`set`/`profile`/`default`), because "inherited" was one bit when there was one thing to inherit from. A per-server policy has **no** process-wide default any more: that layer decided things for servers whose staff could not see the operator's file, and made every "why did Mai do that?" a question with three answers. The one exception is `name-check`, whose default is still `config.moderation.nameCheck` because the same variable decides whether the privileged intent was requested at login; it is deliberately absent from `BASE_SETTINGS`. A new setting = migration column + entry in the `SETTINGS` map (with its parse/validate rule) + option on `/mod config set` + a key in `inherited` (two settings tests assert that map wholesale) + usually an entry in `BASE_SETTINGS`, whose values are public-name/typed-value pairs run through the same `parse` at import (`compile`), so a bad bundle fails at startup rather than when somebody earns a timeout. `effectiveSettings(null)` is valid and yields base values, which is what DMs get. `pick` uses `??` and never truthiness: `''` is a real value at every layer (`flood: ''` is "off here", `link-domains: ''` under an allowlist is "nothing is allowed"). A setting whose value is a *list* still lives in the `SETTINGS` map as a comma-separated column, but gets its own subcommands for editing when its entries are ids: nobody types channel ids into `/mod config set` (`/mod exempt add|remove|list`). `link-domains` is the counter-example and stays a plain option, because host names are what a moderator reads and writes anyway.
- **The provider's verdict is not the guild's verdict** (`applyPolicy` in `src/ai/moderation.js`): `createModeration` returns the booleans *and* `category_scores`, and each guild chooses which decides. A `threshold` above 0 replaces the provider's `flagged` entirely (it has to, or raising the threshold could never make anything pass) and `categories` is an allowlist applied on top. This exists for a measured reason: omni-moderation scores the same insult 0.88 in English and 0.20 in German, so its own line leaves a German server effectively unmoderated. Scores are metadata but only the *highest* one is logged, at debug: a full score vector is a profile of the message.
- **Two layers decide, and the free one goes first**: `src/moderation/heuristics.js` holds the rules a guild enforces without a classifier (invite links, links outside an allowlist, mass mentions, message floods), and `checkMessage` runs them *before* `classifySafely`, so a message they trip on is never sent to the provider. They exist because a moderation score judges what a message means and none of these are about meaning, because they cost no tokens, and because they keep working during an outage, which is when a raid is cheapest to run. They emit ordinary category slugs (`invite`, `link`, `mentions`, `flood`) and go through the same `flagMessage` path as a classified verdict: same grace period, same queue row, same strike. **No separate instant-delete route**, deliberately: one pipeline means one way to undo a false positive. The flood rule is the only stateful one and trips **once per burst** (a cooldown of one window after a trip), because a strike and a scold reply per message would have Mai out-spamming the spammer; it is skipped on edits (`localViolations(..., { rate: false })`) since editing is not sending, while the content rules do run on edits or "post clean, edit the invite in" would walk past all of them. Every rule is off by default: these are house rules, not a safety floor.
- **"Off" and "not configured" are different answers**: the guard settings store an explicit empty value rather than NULL when a guild switches one off (`flood: ''`, `link-domains: ''`), because NULL means inherit and a guild that turned a rule off must not silently pick the process default back up. `effectiveSettings` therefore tests `== null` on those columns, never truthiness, and `/mod config reset <name>` is the only way back to inheriting.
- **Failing open must not fail silently**: `src/moderation/health.js` counts consecutive classification failures per guild and turns them into exactly two log-channel entries, `LOG_DEGRADED` after `MODERATION_DEGRADED_AFTER` and `LOG_RECOVERED` on the next success. One of each per outage (the `announced` flag), because an entry per failed message is a second flood on top of the first, and per guild because the entry is for that guild's staff. The operator already learns about it through the `error` log and the alert hook; this is the half of the audience that could not. `/mod status` reads `degradedGuildIds()` for the same reason: a guild with no log channel has no other route. The reason in the entry goes through `explainError`, never `err.message`.
- **Mai looks after her own setup, because nobody else does**: three separate mechanisms, and they share the property that the failure they prevent is *silent*. `src/gateway/events/guild-create.js` introduces her once per server, with the presets as buttons; `onboarded_at` is written **before** the send so a failure cannot queue a second attempt on the next reconnect, and it is bookkeeping rather than a setting (not in `SETTINGS`, and `configuredGuildCount` counts settings columns rather than rows so a greeting does not make a server look configured). `src/permissions.js` checks what she is missing, scoped to what that guild switched on, once per process plus on join plus in `/mod status`, at `warn` rather than `error` because an under-configured server is not an incident. The enforcer's `watchdog` exits the process when the loop stops making progress, so the compose restart policy (`unless-stopped`) produces a working one: it measures `status.lastProgressAt` (bumped per resolved row), **not** tick completion, or a long pass through a backlog under a rate limit would be killed and restarted into the same backlog forever.
- **A preset is a layer, not a copy** (`src/moderation/presets.js`): `/mod setup` and the onboarding buttons go through `setProfile`, which stores the *name* in `guild_settings.profile`; the values stay changeable with `/mod config set` and resettable with `/mod config reset`, and improving a bundle reaches every server already on it. `setProfile` also **clears the explicit overrides for every key in `PROFILE_KEYS`**, or a server that ran `standard` before profiles existed would switch to `strict` and keep the old numbers; keys no bundle mentions (`log-channel`, `exempt-channels`) are left alone, being facts about the server rather than a stance on moderation. Three rules for any new bundle: never include `enabled` (applying a preset must not undo `/mod off`), never guess a `threshold` for a server nobody has looked at (`observe` plus `/mod simulate` is how that number gets chosen), and remember that adding a key widens `PROFILE_KEYS`, so `/mod setup` will start clearing it. The name can arrive from a `custom_id` **and** from the database, so both `preset()` and `profileRowFor` look it up with `Object.hasOwn`; an unknown stored name falls through to the base rather than throwing on every flagged message. `profile` is deliberately not in the `SETTINGS` map: `/mod config reset` (which clears every override) must mean "put everything back the way my profile has it", not "silently unconfigure the server".
- **The observation period ends with a number, not a homework assignment** (`db/shadow-scores.js`): every message classified during shadow mode is counted into a per-guild histogram (20 buckets of 0.05, keyed on the **top** score), and `learnThreshold` in the enforcer reads the worst `TARGET_SHARE` (1%) off it, applies it as an ordinary explicit `threshold`, announces it with the sample count and attaches an undo button. Counted for **every** classified message and not only flagged ones, which is the whole point: a histogram of what already cleared the line cannot show that the line is too high, and "too high for German" is the case it exists for. Four refusals, all deliberate: fewer than `MIN_SAMPLES` (200) suggests nothing, a percentile outside `[FLOOR, CEILING]` (0.15-0.6) suggests nothing (a polite server must not learn that its mildest 1% is a violation, nor a terrible week that only 0.9 counts), a guild that already set `threshold` itself is never overruled, and a throw anywhere in here costs the measurement rather than the end of the observation period. The histogram is read once and dropped, so the next window cannot inherit the last one's traffic. It is aggregate by construction: no id, no timestamp, no content, same rule as `shadow_hits`.
- **She stops doing what she cannot do** (`reconcileEscalation` in `permissions.js`): missing Moderate Members means every timeout fails at `error`, which reaches the alert channel, on every second strike forever. So escalation goes off, the guild's log is told, and strikes keep counting (which is what escalation-off has always meant). `escalation_suspended_at` is what makes it reversible without overruling anybody: she restores only a suspension of her own, and `updateSettings` clears the marker whenever a patch touching `escalation` carries an `actorId`, because that is precisely the difference between staff's decision and hers. `known: false` (her member object is not cached) is not evidence and is ignored, or the ladder would switch itself off on every cold start. `source` has a fourth value for exactly this setting, `self`, so `/mod config view` does not render her suspension as a colleague's decision: one of those is undone by granting a permission and the other by having a conversation.
- **A log channel is found rather than waited for** (`moderation/log-channel.js`, called from `guild-create.js`): adopt a channel whose whole name matches `^(mod|moderation|mai)[-_]?logs?$`, else create one if she has Manage Channels, else say so in the introduction. The narrow pattern is a privacy decision, not a fussy one: adopting `#changelog` would start posting member ids and category slugs into a channel nobody meant for that. A created channel denies `@everyone` `ViewChannel` on creation (default to less exposure), a channel she cannot write in is not adopted, and a guild that already set `log-channel` is never overruled. Every outcome is named in the introduction, because making a channel in somebody's server is a visible act.
- **An observation period is a promise with a date on it**: `/mod setup observe` writes `shadow_until` (a week out, `SHADOW_DAYS` in `config.js`) and the enforcer tick switches the guild back to enforcing when it passes, announcing it with the count of what she would have acted on (`shadow_hits`, bumped per verdict in `shadowReport`). It exists because the introduction promises "I watch, then I act", and a flag somebody has to remember to turn off is not that promise. `expireShadowWindows` finds and flips in the same statement, so two overlapping ticks cannot both announce it. The counter is per guild and never per member: nobody was told, and nothing happened to them. Anything that states an intent about shadow mode (another preset, `/mod config set shadow:…`) clears the window, or a stale end date fires days later and announces the end of an observation nobody was running. There is deliberately **no process-wide shadow flag**: `MODERATION_SHADOW` was retired into `deprecatedEnv` (logged at startup by `index.js`) because it could only produce shadow mode without a shape, on everywhere and forever.
- **Shadow mode reports and acts on nothing** (`shadowReport` in `check.js`): both verdict layers run, then the guild's log gets a `LOG_SHADOW` entry with the categories and the **top score** (never the vector, same rule as the debug log) and the pipeline returns `OK`. Nothing else may happen: no reaction, no scold, no queue row, so `openViolations` stays empty and Mai's chat tone does not change either. It is deliberately **not** a pause: a row queued before shadow was switched on is still enforced and still cleared by an edit, because abandoning pending enforcement silently is what `/mod off` is for. The message is untouched, so `LOG_SHADOW` belongs in `MESSAGE_ALIVE` and its jump link resolves.
- **The full score vector has exactly one caller**: `simulate()` in `ai/moderation.js`, its own exported function rather than a flag on `classify`, so "who can see a profile of a message?" stays greppable. What makes `/mod simulate` acceptable is the combination: the text is the moderator's own, the answer is ephemeral to them, and nothing is stored or logged (the log line carries category slugs, never the text). Do not point it at member messages.
- **Staff acting through Mai has to land on the same record she uses**: `commands/remove.js` (the `Löschen (Mai)` context menu) deletes and writes `ACTION_DELETED`, so a human's decision counts on the ladder like hers; `/mod warn` writes `ACTION_WARNED`, which `strikeCount` does **not** count, because a moderator having a word must not silently move somebody towards a timeout. Two traps in the manual deletion: any message Mai may have flagged must be registered with `markOwnDeletion` before it goes, and a **pending queue row for it has to be dropped with its scold reply** or the next tick reads the missing message as the author having fixed it and writes a self-deletion over the strike that was just recorded. The deletion is deferred for staff only (a refusal is one line and needs no round trip), and the target channel's guild is proven against `interaction.guild_id` before deleting, because the bot's client reaches every guild Mai is in.
- **`member_notes` is staff's own text, so it is not the third content exception**: plaintext, unlike `chat_history` and `evidence`, because those hold what a member wrote and this holds what staff wrote about their own server, in the same class as a report reason (which is already posted into a Discord channel in the clear). Still pruned on `VIOLATION_RETENTION_DAYS`, so it cannot become an unbounded file on a person, and still only readable through `/mod history`, which is ephemeral and staff-only.
- **`evidence` is the second exception to the no-content rule, and its limits are the feature** (`src/db/evidence.js`): the enforced message's text, AES-256-GCM under the same key as `chat_history`. It exists because staff deciding an appeal had ids and category slugs and nothing else, so "das war nur ein Zitat" came down to the member's word against Mai's. Two switches, deliberately: `MODERATION_EVIDENCE_HOURS` (the operator's database) *and* the per-guild `evidence` flag (the guild's members); `effectiveSettings` folds the first into the second, so `evidenceEnabled` is what actually happens. Written by the enforcer at the moment of deletion (never anywhere else), pruned by the tick with a cutoff of `now - hours`, which at 0 hours clears the table, so turning the feature off cleans up after itself. Read back **only** through `appeal-evidence`: Manage Messages-checked, ephemeral (posting it into the channel would undo the deletion it documents), scoped to `interaction.guild_id` rather than the id in the `custom_id`, and to the incident's `since` rather than the member's record. The button is only attached where evidence is actually kept, and the text is never logged, not even at debug: it is already stored deliberately, and a copy in the container log would have a different lifetime. `/mod forgive … strikes:true` drops it; `/mai forget` deliberately does not, because the person being reviewed must not be able to delete the review's material.
- **A display name is a violation no message rule can see** (`src/moderation/names.js`): screened on join and on rename, gated by `name-check` (`off`/`log`/`reset`). Three constraints that are easy to get wrong: it **fails open** (an unreachable classifier must never become "strip this member's nickname", which is why it uses `classify` directly rather than `screenInput`, whose fail-closed rule is for text Mai would republish); the ceiling is a nickname reset, never a kick or a ban, and a *global* username is not Mai's to change at all, so that case ends in an entry and a human; and the log entry carries **no copy of the name**, because `<@id>` renders as the member's current display name for whoever reads it. `guildMemberUpdate` fires for roles, avatars and every timeout Mai hands out, so the handler compares display names first: without that, timing someone out immediately re-screens them. A per-member limiter (3 per 10 minutes) bounds a rename storm.
- **Member events are one intent and two features**: `GuildMembers` is privileged and requested by `DISCORD_MEMBER_EVENTS` alone (`config.discord.memberEventsEnabled`), which says only what the Developer Portal says. The two features that ride it (`welcome`, `name-check`) are ordinary per-guild settings, folded against that switch inside `effectiveSettings` so a caller reads what actually happens; `onGuildMemberAdd` runs for either and checks `welcomeEnabled` itself before greeting. Splitting them this way is the fix for a policy that used to double as an intent request: a deployment could not greet in one server and not another, and switching the policy off in the last server that wanted it pulled the intent out from under the other feature. Order matters there: the name is screened first and a flagged name is not welcomed, because a welcome mentions the member and would put that name in front of the server in Mai's own words. An intent is a process-wide decision made once at login, so a guild setting can never turn one on: `/mod config set name-check` (and `evidence`, for the retention window) stores the value anyway and answers with a warning that the operator has not enabled it, because silently accepting a setting that does nothing is how a server ends up believing it is protected.
- **An enforcement nobody was told about is not finished**: a warning DM that throws is normal for the process (closed DMs) and stays at `info`, but the member has lost messages, possibly earned a timeout, and never saw the appeal button, so the enforcer posts `LOG_WARNING_UNDELIVERED` into the guild's log. `/mai appeal` is the member's own route back in: it rebuilds the `since` the DM button would have carried from the strike record (`lastEnforcementPass` in `db/violations.js`, grouping by the gap between rows because a tick writes its strikes seconds apart), scoped to the strike window. It answers with a modal, so like every modal opener it must stay synchronous, and it refuses without a log channel like reports do.
- **Channel exemptions are a scope statement, not a pause**: `isExemptChannel(guildId, channelId, parentId)` (exported from `check.js`) gates `isModeratable`, and the enforcer **drops** pending rows in a newly exempt channel rather than keeping them: staff saying "Mai does not moderate here" must not be followed by her deleting something there ten minutes later. A thread is covered by exempting its parent. Exemption is moderation-only: chat and reactions keep working, which is the point for a vent channel.
- **The moderation log is metadata only**: `src/moderation/log.js` posts embeds to the per-guild `log-channel`. A Discord channel is permanent storage readable by everyone with access, so message content must never go into it: ids, category slugs, timestamps and a jump link only. **That includes `err.message`**: an exception message is free text that can quote a channel name, a config value or a request body, so nothing reported to Discord is ever built from one. `src/errors.js` has the two functions that replace it, split by audience: `describeError()` (name plus `status`/`code`) is for the operator and is what `alerts.js` forwards, and `explainError()` is for a guild's staff, mapping the Discord codes that actually occur onto sentences in `moderation.errors` in the YAML and appending the code so they can hand it on. An unmapped code degrades to `describeError`, so a new one is still safe, just less helpful: add it to the YAML rather than reaching for the message. The full message stays in the container log, which is where the operator already is. `postModerationLog` also proves the channel it fetched is in the event's own guild before sending: the id comes from settings, but the fetch goes through the bot's client, which reaches every guild Mai is in. (There is no footer saying so: the rule is enforced in code, and a disclaimer on every entry was noise staff never acted on.)
- **Every log entry starts with the same head**: `fieldsFor` builds `[user, channel, message]` and each kind appends to it, so following one incident across *flagged → deleted/cleared/self-deleted → appeal* never means hunting for the message id in a different field or finding it absent. `messageField` renders the id in a code span always, plus a jump link only for kinds in `MESSAGE_ALIVE`: a link to a deleted message is a 404, but the id still correlates with Discord's audit log. The offender's warning DM stays the sole place their text is quoted. The **one** exception is text a member wrote *for* staff and submitted themselves: a report reason and an appeal statement. Never widen it to copied message content. Posting is best effort and never blocks the pipeline; the `flagged` entry is fired detached because `onMessageCreate` awaits that verdict.
- **Opening a modal cannot be deferred; submitting one must be**: Discord opens the modal as the immediate response, so a handler that returns `modalResponse` must do synchronous work only (`report.execute`, `appealButtons.appeal`). The *submit* handler is the opposite case and both of them (`reportModals.report`, `appealModals['appeal-submit']`) set `deferred = true`: publishing to the log channel is a fetch plus a send, two Discord round trips that outlast the ~3 s budget under a rate limit, and the cost of blowing it is the member's typed report or appeal, which they cannot get back. Unconditional, unlike `report-approve`: these answers are ephemeral either way, so no refusal can overwrite a log entry. Everything the submit handler needs must travel in the modal's `custom_id`: the resolved data of the original interaction is gone by then, and the 100-character id limit is the real budget (`report:<channelId>:<messageId>:<authorId>` is 65).
- **Features that need a place to write check for it first**: reports and appeals both refuse with an explanation when the guild has no `log-channel`, and the appeal button is not attached to a warning DM at all in that case. Never queue user-visible work that has nowhere to land.
- **All SQL lives in `src/db/`**: `queue.js` (moderation queue), `history.js` (chat memory), `settings.js` (per-guild overrides), `violations.js` (strike record), `evidence.js` (appeal evidence), `notes.js` (staff notes) and `usage.js` (token counters) are the repository modules; nothing outside the directory prepares a statement or imports `node:sqlite`, read-only aggregates included. A reader that needs a number the repositories do not expose yet gets a function there, never its own query: `/metrics` used to prepare its own, which is how a second definition of "overdue" came to exist next to the enforcer's and drift from it (`maxAttempts`, `countsByAction`, `configuredGuildCount` are what it uses instead). Schema changes are new numbered files in `src/db/migrations/` (applied in a transaction at startup, recorded in `schema_migrations`): never edit an applied migration. The database file must live on the `mai-data` volume; the rootfs is read-only and `/tmp` is a tmpfs.
- **Moderation fails open**: if classification fails (API down, key revoked, timeout), `checkMessage` returns `{ action: 'ok' }` and the message passes. Chat keeps working. A failure to *enqueue* is logged at `error`: the message is scolded but will never be enforced, which must stay visible. The one deliberate exception is `recheckMessage` on a message that **already has a queue row**: no verdict is not the same as innocent, so the row stands rather than being forgiven by an outage.
- **A self-deletion resolves on the event, not at the deadline** (`src/gateway/events/message-delete.js` → `recordSelfDeletion` in `check.js`, shared with the enforcer's fallback for a deletion that happened while the gateway was down). The catch is that `messageDelete` never says *who* deleted the message: Mai's own enforcement, an approved report and her scold-reply cleanup all fire it too, and would otherwise be recorded as the author having fixed it: a strike silently downgraded. So every deletion Mai performs is registered through `markOwnDeletion` (in `cleanup.js`, with a TTL so a failed delete cannot leak an entry) and skipped by the handler. Any new code path that deletes a message Mai may have flagged must mark it.
- **Discord never times out an admin or the owner**, so `applyTimeout` checks for that *before* trying and returns a normal refusal at `info` level. Letting it fail through the catch would log at `error` and page the operator through the alert hook every single time such a member trips the ladder: a permanent property of the target is not an incident. The log-channel entry still goes out; staff should know the ladder had no effect.
- **Edits are moderated, and un-moderated, by `recheckMessage`** (`src/moderation/check.js`, wired through `src/gateway/events/message-update.js`): without it the edit button bypasses the whole pipeline. Unlike `checkMessage` the verdict is four-way, because the message may already be queued: new violation → flag it; still a violation → `updateCategories` only, the `due_at` deliberately stays put (editing one slur into another must not buy a fresh grace period) and there is no second scold; no longer a violation → `clearFlag` undoes everything the flag added (warning reaction, scold reply, queue row) and posts `LOG_CLEARED`, so a `flagged` entry in the log never evaporates unexplained. `clearFlag` deletes the queue row **first**, so a tick starting concurrently cannot still enforce a fixed message. The correction is recorded as `ACTION_EDITED`: on the record, deliberately not a strike, exactly like `ACTION_SELF_DELETED`. Discord fires `messageUpdate` for link previews, pins and flag changes too; `isContentEdit` filters those on `edited_timestamp` plus a content comparison so they cost no classification call. Edits are moderation-only: a mention retrofitted into an old message must not trigger chat.
- **Undoing Mai's marks lives in `src/moderation/cleanup.js`**: `deleteMessageById` and `removeWarningReaction`, shared by the enforcer and `clearFlag`, both best effort. The reaction removal prefers the cached reaction but falls back to the `/@me` REST route, because a MESSAGE_UPDATE payload does not reliably carry `reactions`: never `removeAll()`, which would drop other members' reactions too.
- **OpenAI retries are safe**: an API call has no side effects of its own, and Discord actions only happen in our code after it returned, so 429/5xx/network errors **and** timeouts are retried with backoff (`src/ai/openai.js`).
- **Enforcement is per-row and idempotent**: the tick loop (`src/moderation/enforcer.js`) skips overlapping runs, and each row either resolves (row deleted) or is kept for the next tick. Rows are processed **serially and capped** at `MODERATION_MAX_ROWS_PER_TICK`: each row is several Discord calls, so parallelism only trades a shorter tick for a harder rate limit, and without the cap a backlog could outlast the interval and be skipped by the overlap guard forever. `dueRows` orders oldest-first so a capped tick still drains in order; exceeding the cap is logged at `warn`. **Oldest-first plus a cap means any row that is kept but can never resolve occupies the cap forever**, so a category of row like that has to be excluded from the query itself, not skipped inside the loop: paused guilds (`pausedGuildIds()`) are filtered out in SQL, and the per-row `isGuildActive` check is only the guard for a guild paused mid-tick. That exclusion is itself filtered by `isGuildAllowed`: a guild that is *both* paused and no longer allowlisted must stay in the query, because dropping its rows is the allowlist check's job and it only runs on a row the tick actually picked up. Discord error codes 10008/10003 mean "author deleted it"; any other lookup *failure* must keep the row, never silently drop it. Two neighbouring cases are deliberately not failures and are told apart: `channels.fetch` answering **null** is a successful lookup that found nothing, so it resolves like a 10003 rather than retrying an hour for a channel that is not coming back; a channel that resolves but has no `messages` (a category, a voice channel) is the opposite and must **not** be reported as 10003, because that would record the author as having deleted their message and quietly downgrade a strike. The latter is a failed attempt (`not_text_channel`), which counts and eventually gives up. A row that *throws* instead of reporting its failure is put through `reportFailure` too, or it would retry every tick without ever reaching the give-up threshold. The channel is fetched **before** the exemption check, because an exemption covers the exempted channel's threads and the parent id is only knowable from the channel object. The same tick prunes chat history, so retention does not depend on someone talking to Mai.
- **Member events need a privileged intent**: the `GuildMembers` intent is only requested when `DISCORD_MEMBER_EVENTS=true` (`config.discord.memberEventsEnabled`): setting it without switching on "Server Members Intent" in the Developer Portal makes the gateway login fail. Don't add the intent unconditionally, don't gate a *handler* on one feature's setting when both ride on it, and never let a per-guild setting decide an intent: intents are chosen once, at login, for the whole process.
- **Direct messages are chat-only, and allowlist-gated by membership**: a DM has no `guildId`. `isMaiChatTrigger` treats any DM as addressed to Mai (no mention required), but `onMessageCreate` first calls `isDmAuthorInAllowedGuild`: the DM is dropped unless the author shares at least one `DISCORD_GUILD_IDS` guild with the bot (empty allowlist = open). This is a per-member REST fetch (`guild.members.fetch(id)`, no privileged intent needed), the DM equivalent of the guild allowlist. It runs *before* any chat rate limit, so the answer is cached per user (positive 10 min, negative 30 min; a stale "no" costs a new member a wait, a cache miss costs a round trip per guild per message) with a small per-user limiter behind the cache for repeated misses. The cache is the real protection; the limiter only bounds the post-expiry case. `onMessageCreate` skips moderation for DMs: a bot cannot delete a user's DM, so the delete/scold pipeline has nothing to enforce. DMs need the non-privileged `DirectMessages` intent **plus** `Partials.Channel` (both in `gateway/client.js`); no Developer Portal toggle. Chat history is keyed by `channelId` precisely so DMs work without a guild id.
- **Chat tools take no model-supplied arguments and are synchronous** (`src/chat/tools.js`): every tool's `parameters` is an empty object, and the caller's id, guild and client come from the interaction context passed to `runTool`. `runTool` does not await, so a handler must never return a promise: `get_my_timeout_status` reads the member **cache** and answers `unknown_member` on a miss rather than fetching (a member talking to Mai right now is cached by their own message). A tool with nothing to say is not offered at all rather than answering empty: `get_server_rules` is left out of `toolDefinitions` when `chat.rules` is empty, because a tool that returns "no rules" sends the model straight back to inventing them, which is what the tools exist to stop. A tool that accepted a user id from the completion would let a prompt-injected model read another member's moderation record. Keep new tools argument-free, or validate against the context: never trust the arguments string. The tool *name* is equally model-supplied, so the handler table is looked up with `Object.hasOwn`: a bare property read also answers for `Object.prototype`, and `constructor` resolved to `Object`, which `runTool` then called with the chat context and returned it verbatim for serialization. Serializing a result is wrapped too (`toolPayload` in `ai/chat.js`), so one unserializable result costs a tool call rather than the whole reply.
- **The tool loop echoes the assistant message verbatim**: an assistant message carrying `tool_calls` must be pushed back into `messages` unchanged before the matching `{ role: 'tool', tool_call_id }` results, or the provider rejects the follow-up. `MAX_TOOL_ROUNDS` caps the rounds and the final call deliberately omits `tools`, so a confused model cannot bill an endless loop.
- **Prompt context is not memory**: the quoted replied-to message, the thread title and image URLs go into the prompt but are never persisted: `chat_history` keeps only what the member wrote themselves (an image-only message becomes a placeholder). Discord CDN links expire anyway.
- **LLM output never pings**: Mai's replies are posted with `allowedMentions: { parse: [] }` and `normalizeReply` neutralizes `@everyone`/`@here` with a zero-width space. Keep both when touching the chat path.
- **Text a member asks Mai to repeat is classified; what Mai says herself is not.** `screenInput` (`src/moderation/screen.js`) guards `/mai ask`, whose answer quotes the question back into the channel: the one path publishing a member's words without `checkMessage` seeing them. It fails **closed** (no deletion path exists to undo a repeat) and runs *before* the completion, so a refusal costs no tokens. There is deliberately **no outbound screen on her replies**: the persona escalates with a member's open violations and the top tone instructs her to insult them outright (`chat.flagged.tones`, "Beleidigungen erwünscht"), which a classifier scores as harassment 0.89–0.98: screening would replace the angry cat with a canned line exactly when she is meant to be angry. The behaviour is the feature; the guard against a prompt-injected model is the prompt (`fenced()`, `prompt.untrustedNotice`), not a filter on the way out. Don't re-add one without a category allowlist that excludes `harassment`.
- **Only the system message carries instructions**: `buildMessages` appends `prompt.untrustedNotice` to it, and text the speaker merely *chose* to pull in (the quoted replied-to message, the thread title) is wrapped in `⟪…⟫` by `fenced()`, which strips those characters from the value first so it cannot close its own fence. Speaker labels run through `speaker()`, which strips newlines and colons so a username cannot forge a second `Name:` turn. The current speaker's own message is deliberately *not* fenced: it is the thing being answered, and fencing it would fight the persona.
- **Guild targeting**: `DISCORD_GUILD_IDS` is the whole-bot allowlist: routed through `isGuildAllowed(guildId)` in `config.js` and enforced at each entry point (`onMessageCreate`, `onMessageUpdate`, the `/interactions` command handler, `guildMemberAdd`) plus defensively in `checkMessage`/`recheckMessage` and the enforcer, so an un-listed guild gets no behavior at all. A guild removed from the allowlist also drops its pending queue rows on the next tick. DMs have no guildId and use `isDmAuthorInAllowedGuild` instead.
- **`enqueue` upserts, it does not `INSERT OR REPLACE`**: the latter is a delete plus an insert, so every column not named in it silently returns to its default. `attempts` is the one that matters: a stuck row re-flagged by an edit would forget how often it had already failed and never reach the give-up threshold. Any column added to this table needs the same treatment.
- **Privacy queue schema**: `moderation_queue` holds `message_id, guild_id, channel_id, user_id, categories (JSON), warned_at, due_at, scold_message_id`: metadata only, never content. The text quoted in a warning DM is read live from Discord at enforcement time (`cleanContent`) and is never written to the database. The queue doubles as the "is this user currently flagged" source that flips Mai's chat tone (`openViolations`, matched on `user_id` across **all** guilds, DMs included).
- **Two content stores, both exceptions, both encrypted**: `chat_history` (messages addressed to Mai) and `evidence` (messages she enforced, see above). `content`/`username` are AES-256-GCM ciphertext (`src/db/crypto.js`, key `CHAT_HISTORY_KEY`, required as soon as either feature is on); the lookup and pruning keys (`channel_id`, `sent_at`, `guild_id`, `created_at`) stay plaintext. Rotating the key makes old rows undecryptable, they are skipped and pruned, never crash a reply or an appeal review. Nothing else in the database holds content, and a third exception needs the same treatment as these two: off by default, encrypted, short retention, one narrow reader.
- **Chat guards** (`src/chat/limits.js`): per-user rate limit and a global concurrency cap fail closed with the busy emoji instead of a reply, and turns are serialized per channel so parallel conversations cannot interleave history reads and writes. Keep the serialization around any change to the read-history → reply → store sequence.
- **Logging privacy rule**: message content is never logged at `info`: metadata only; content appears at `debug` level only. This covers **both directions**: inbound message text, Mai's replies, prompts, and warning-DM bodies. Usernames are content too; `userId`/`authorId` snowflakes, category slugs, model names and timings are metadata and may be logged at info.
- **Hardened containers**: `read_only` rootfs, `cap_drop: ALL`, tmpfs-only writes, non-root `node` user, plus the `mai-data` volume as the single writable path. Code writing anywhere else will fail at runtime. Compose v2.40 quirk: `pids_limit` cannot coexist with `deploy.resources.limits`: the pid limit lives at `deploy.resources.limits.pids`.
- **Two gates per guild, and they are not the same**: `isGuildAllowed(guildId)` is the operator's allowlist (`DISCORD_GUILD_IDS`) and drops pending queue rows; `isGuildActive(guildId)` in `src/db/settings.js` is the server's own kill switch (`/mod off`) and *keeps* them: a pause, not an amnesty. Both are checked at every entry point, allowlist first. The router deliberately lets `/mod` through while paused, otherwise switching Mai back on would need database access.
- **A staff decision must land in the channel, not in an ephemeral reply**: the report buttons *and* the appeal buttons edit the log entry itself (title, colour, resolution field, buttons removed) so every moderator sees the outcome. An appeal decision additionally DMs the member: an appeal that vanishes into a staff channel is not an appeals process. Granting **overturns the strikes it is about**: `overturnSince` flips them to `ACTION_OVERTURNED`, which removes them from `strikeCount` (it only counts `ACTION_DELETED`) without deleting the rows, so the record still shows that Mai was wrong and it was corrected. The scope comes from the enforcement pass, carried as epoch seconds through `appeal:<guild>:<since>` → `appeal-submit:<guild>:<since>` → `appeal-grant:<user>:<since>`: an appeal against one incident must not clear four earlier, correct strikes. Staff who *do* mean the whole record run `/mod forgive <user> strikes:true`. Settings changes post a `LOG_CONFIG` entry for the same reason: `updated_by` in a database nobody can read from Discord is not visibility, and `/mod off` is exactly when the rest of the team needs to know. When such a handler is deferred for latency, the deferral has to be conditional on the clicker being staff: after a defer the response is public, and a permission refusal would overwrite the entry (`reportComponents['report-approve'].deferred`).
- **Two moderation stores, different lifetimes**: `moderation_queue` is *pending* enforcement and is emptied when a row resolves (enforced, forgiven, or edited clean); `violations` is the long-term strike record (`src/db/violations.js`, metadata only, pruned after `VIOLATION_RETENTION_DAYS`). Mai's chat tone still reads the queue (an *open* violation makes her hiss) while escalation counts the record. Don't conflate them: a member with an empty queue and ten strikes is friendly-Mai but next-step-on-the-ladder.
- **An incident is one member in one guild in one tick**, and both the timeout and the warning DM are scoped to it. `groupByMember` (`moderation/warning.js`) is the single grouping pass, keyed by `memberKey(guildId, userId)`, and `escalate()` consumes those same groups so the two cannot drift: three messages removed in one sweep is one incident, not three timeouts. **Never group on the user id alone.** Mai serves several guilds from one process, so one person can be enforced in two of them in the same tick, and merging those produced a DM that quoted one guild's deleted messages next to another's, with an appeal button scoped to whichever guild sorted first (granting it then overturned the wrong strikes). Only `action = 'deleted'` counts; a message the author removed during the grace period is recorded and deliberately does not escalate. The ladder's ceiling is a timeout: Mai must never kick or ban on her own, because an automated permanent action on a false positive is not recoverable. A refused timeout (missing Moderate Members, role hierarchy, admin or owner target) is logged at `error` and shown in the log channel, never swallowed.
- **Alerts ride on the logger, so they must never log**: `src/alerts.js` is called from a pino `hooks.logMethod` for level ≥ 50, forwards only whitelisted keys (a log record may carry content, an alert must not), and swallows its own failures: logging there would feed itself. `err.message` is **not** forwarded either, only the error's name plus `status`/`code`: the alert channel is permanent Discord storage, and an exception message is free text that can quote config, a database value or a request body. The full message stays in the container log. It imports config only at the top; the gateway client is pulled in dynamically because logger.js imports this module. Two properties to preserve: a `LOG_LEVEL` above `error` disables the hook with the level (pino no-ops disabled methods), and the throttle must not be turned into a re-entrancy guard: that drops concurrent alerts, not recursive ones.
- **Token accounting is recorded where the response is parsed** (`ai/openai.js` → `db/usage.js`), never at call sites, and it is wrapped so a failing counter cannot fail a call that already succeeded. `OPENAI_MONTHLY_TOKEN_BUDGET` gates chat only: moderation must keep running when the budget is gone.
- **Tests are host-only** (`npm test` in `mai/`): `node:test`, no dependencies, no network: OpenAI and Discord are stubbed through global `fetch`. `test/setup.js` must be imported before anything else because `config.js` reads and validates the environment at import time. Each `test/setup-*.js` prepares one shape of configuration for the files that need it (`-chat`, `-moderation`, `-gateway` for both at once, `-security`, `-limits`, `-enforcer`, `-http`, `-metrics`, `-alerts`, `-openai`, `-presence`, `-health`, `-evidence`, `-names`, `-welcome`) and must be imported *before* `setup.js`. The `test/` directory is deliberately not copied into the image.
- **`/healthz` is a real probe**: it reports database reachability and the age of the last moderation tick (three missed ticks = 503, with a startup grace period before the first one). Keep it cheap: the Docker healthcheck hits it every 30 s. It only *reports*, though: acting on a wedged loop is the enforcer's own watchdog, because a Docker restart policy does not watch health.
- **`/metrics` is operator-only and off by default** (`src/http/metrics.js`): the same numbers `/mod` shows, but process-wide, on a server that is public through the tunnel, so it 404s unless `METRICS_TOKEN` is set and then wants it as a `Bearer` token, compared with `timingSafeEqual`. The scheme is required, not stripped-if-present. Labels stay low-cardinality (`purpose`, `model`, `action`): **never** label by guild, user or channel: that turns a metrics series into a per-member activity record, and it is unbounded besides. `mai_queue_overdue` counts only what a tick would actually act on and `mai_queue_paused` counts what is parked, because a paused guild's rows sit past `due_at` forever by design and counting them as overdue made the alerting signal fire on a server that had simply run `/mod off`. Both reuse the enforcer's own exclusion list so the numbers cannot drift from its behaviour.
- **Reaction triggers must not be stateful**: `content.js` strips `g` and `y` from the YAML `flags`, because the patterns are used with `.test()` and either flag walks `lastIndex`: the same message would match, then not, then match again. A reaction firing every other time is not something anyone would go looking for in a config file.
