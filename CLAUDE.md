# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Discord moderation system in two parts:

1. **`mai/`** — Node.js 24 ESM app (discord.js + express + discord-interactions + pino + yaml). Runs two Discord connections side by side: an HTTP interactions endpoint (`POST /interactions`, slash commands, reached through cloudflared) and an outbound gateway WebSocket (`messageCreate`, `guildMemberAdd`). Moderation and chat run in-process: OpenAI-compatible HTTP calls for classification and replies, SQLite (`node:sqlite`) for state, and an interval timer that enforces the grace period. The bot has a persona — **Mai**, the server's cat: mention/reply/DM chat, keyword emoji reactions, optional welcome messages, custom presence. Everything she says lives in `mai/config/mai.yaml`.
2. **`docker-compose.yml`** — stack of `mai` + `cloudflared` on the `edge` network, plus the `mai-data` volume for the database.

Full details: [README.md](README.md), [mai/README.md](mai/README.md).

## Commands

```sh
docker compose up -d --build mai   # rebuild + restart bot after code changes
docker compose logs -f mai         # structured pino JSON logs
docker compose run --rm mai npm run register   # sync slash commands with Discord
npm test                           # (in mai/) node:test, no deps, no network
```

- **`.env` changes require container recreate** (`docker compose up -d mai`). A plain restart does not re-read the env file — this has caused real debugging sessions.
- `.env` holds all secrets (gitignored); `.env.example` is the documented template. Env config is read and validated once in `mai/src/config.js` — add new env vars there, not via scattered `process.env` reads.

## Architecture constraints that aren't obvious from single files

- **Two config surfaces, both loaded once at startup**: `src/config.js` = operational (secrets, models, flags, timings, limits) from the environment; `src/content.js` = everything user-facing, loaded and validated from `mai/config/mai.yaml` (`MAI_CONFIG_PATH`). No handler may contain a literal string Mai says — persona, prompt scaffolding, scold lines, warning-DM template, `/mai` replies, welcome lines, reaction regexes and presence statuses all live in the YAML. Adding wording = YAML key + a validated field in `content.js`.
- **Interactions vs. gateway split**: everything from Discord's HTTP side (commands, autocomplete, buttons, modals) is signature-verified by `verifyKeyMiddleware` — no `express.json()` may run before it on that route — and then dispatched by `src/interactions/router.js`, which is also where the guild allowlist is enforced for all interaction kinds. `http/server.js` stays a thin transport. Message events only exist on the gateway (handler in `src/gateway/events/` + `client.on()` in `src/gateway/client.js`).
- **Interaction deadline and deferral**: Discord needs the HTTP response in ~3 s. A handler that cannot make it declares `deferred` (boolean or `(interaction) => boolean`); the router sends a placeholder, then edits it via the interaction webhook (`editOriginalResponse`) when the handler resolves. Two traps: `ephemeral` is fixed at defer time and the later edit **cannot** change it (`toMessageBody` strips `flags`), so a deferred public command must return public refusals too; and the interaction token expires after 15 minutes, so a failed edit is not retried. `send` is called exactly once per interaction. New slash command = file in `src/commands/` + entry in `src/commands/index.js` + `npm run register`. New button/select/modal = handler map exported from the feature module + entry in `src/interactions/registry.js`.
- **Read command options through `src/interactions/options.js`**: `resolveSubcommand(interaction)` flattens plain subcommands *and* subcommand groups into `{ group, name, options }`, so `/mod config set` and `/mod status` are handled the same way; `optionValue(options, name)` reads a single option. Handlers must not walk `interaction.data.options` themselves — the shape differs between the two cases. This module is deliberately separate from `router.js` to avoid an import cycle (router → command registry → commands).
- **Component state lives in the `custom_id`** (`name:arg:arg`, split by `parseCustomId`) — there is no server-side interaction session. A handler that acts on behalf of a user must verify the id belongs to the clicker (see `forgetComponents`); an ephemeral message is not an authorization boundary.
- **Code reached from the HTTP side has no gateway client of its own**: use `getGatewayClient()` from `src/gateway/client.js`, which is null until the gateway is ready. Slow Discord REST work triggered by a command runs detached (see `cleanUpScolds` in `src/commands/mod.js`).
- **Settings are layered, not duplicated**: `.env` holds the process default, `guild_settings` holds only what a server explicitly changed (NULL = inherit). `effectiveSettings(guildId)` in `src/db/settings.js` is the single merge point — never read `config.moderation.gracePeriodMinutes` (or another overridable knob) directly in a handler. A new setting = migration column + entry in the `SETTINGS` map (with its parse/validate rule) + option on `/mod config set`. `effectiveSettings(null)` is valid and yields defaults, which is what DMs get.
- **The moderation log is metadata only**: `src/moderation/log.js` posts embeds to the per-guild `log-channel`. A Discord channel is permanent storage readable by everyone with access, so message content must never go into it — ids, category slugs, timestamps and a jump link only, with the footer stating it. The offender's warning DM stays the sole place their text is quoted. Posting is best effort and never blocks the pipeline; the `flagged` entry is fired detached because `onMessageCreate` awaits that verdict.
- **All SQL lives in `src/db/`**: `queue.js` (moderation queue) and `history.js` (chat memory) are the only modules with SQL, and nothing else imports `node:sqlite`. Schema changes are new numbered files in `src/db/migrations/` (applied in a transaction at startup, recorded in `schema_migrations`) — never edit an applied migration. The database file must live on the `mai-data` volume; the rootfs is read-only and `/tmp` is a tmpfs.
- **Moderation fails open**: if classification fails (API down, key revoked, timeout), `checkMessage` returns `{ action: 'ok' }` and the message passes. Chat keeps working. A failure to *enqueue* is logged at `error` — the message is scolded but will never be enforced, which must stay visible.
- **OpenAI retries are safe**: an API call has no side effects of its own, and Discord actions only happen in our code after it returned, so 429/5xx/network errors **and** timeouts are retried with backoff (`src/ai/openai.js`).
- **Enforcement is per-row and idempotent**: the tick loop (`src/moderation/enforcer.js`) skips overlapping runs, and each row either resolves (row deleted) or is kept for the next tick. Discord error codes 10008/10003 mean "author deleted it" — any other lookup failure must keep the row, never silently drop it. The same tick prunes chat history, so retention does not depend on someone talking to Mai.
- **Welcome messages need a privileged intent**: the `GuildMembers` intent is only requested when `DISCORD_WELCOME_ENABLED=true` — enabling the flag without switching on "Server Members Intent" in the Developer Portal makes the gateway login fail. Don't add the intent unconditionally.
- **Direct messages are chat-only, and allowlist-gated by membership**: a DM has no `guildId`. `isMaiChatTrigger` treats any DM as addressed to Mai (no mention required), but `onMessageCreate` first calls `isDmAuthorInAllowedGuild` — the DM is dropped unless the author shares at least one `DISCORD_GUILD_IDS` guild with the bot (empty allowlist = open). This is a per-member REST fetch (`guild.members.fetch(id)`, no privileged intent needed), the DM equivalent of the guild allowlist. `onMessageCreate` skips moderation for DMs — a bot cannot delete a user's DM, so the delete/scold pipeline has nothing to enforce. DMs need the non-privileged `DirectMessages` intent **plus** `Partials.Channel` (both in `gateway/client.js`); no Developer Portal toggle. Chat history is keyed by `channelId` precisely so DMs work without a guild id.
- **LLM output never pings**: Mai's replies are posted with `allowedMentions: { parse: [] }` and `normalizeReply` neutralizes `@everyone`/`@here` with a zero-width space. Keep both when touching the chat path.
- **Guild targeting**: `DISCORD_GUILD_IDS` is the whole-bot allowlist — routed through `isGuildAllowed(guildId)` in `config.js` and enforced at each entry point (`onMessageCreate`, the `/interactions` command handler, `guildMemberAdd`) plus defensively in `checkMessage` and the enforcer, so an un-listed guild gets no behavior at all. A guild removed from the allowlist also drops its pending queue rows on the next tick. DMs have no guildId and use `isDmAuthorInAllowedGuild` instead.
- **Privacy queue schema**: `moderation_queue` holds `message_id, guild_id, channel_id, user_id, categories (JSON), warned_at, due_at, scold_message_id` — metadata only, never content. The text quoted in a warning DM is read live from Discord at enforcement time (`cleanContent`) and is never written to the database. The queue doubles as the "is this user currently flagged" source that flips Mai's chat tone (`openViolations`, matched on `user_id` across **all** guilds, DMs included).
- **`chat_history` is the only content store**: a deliberate exception to the no-content rule, limited to messages addressed to Mai. `content` and `username` are AES-256-GCM ciphertext (`src/db/crypto.js`, key `CHAT_HISTORY_KEY`); `channel_id` and `sent_at` stay plaintext as lookup/pruning keys. Rotating the key makes old rows undecryptable — they are skipped and pruned, never crash a reply.
- **Chat guards** (`src/chat/limits.js`): per-user rate limit and a global concurrency cap fail closed with the busy emoji instead of a reply, and turns are serialized per channel so parallel conversations cannot interleave history reads and writes. Keep the serialization around any change to the read-history → reply → store sequence.
- **Logging privacy rule**: message content is never logged at `info` — metadata only; content appears at `debug` level only. This covers **both directions**: inbound message text, Mai's replies, prompts, and warning-DM bodies. Usernames are content too; `userId`/`authorId` snowflakes, category slugs, model names and timings are metadata and may be logged at info.
- **Hardened containers**: `read_only` rootfs, `cap_drop: ALL`, tmpfs-only writes, non-root `node` user, plus the `mai-data` volume as the single writable path. Code writing anywhere else will fail at runtime. Compose v2.40 quirk: `pids_limit` cannot coexist with `deploy.resources.limits` — the pid limit lives at `deploy.resources.limits.pids`.
- **Tests are host-only** (`npm test` in `mai/`): `node:test`, no dependencies, no network — OpenAI and Discord are stubbed through global `fetch`. `test/setup.js` must be imported before anything else because `config.js` reads and validates the environment at import time; `test/setup-chat.js` flips chat on for the one file that needs it and must be imported *before* `setup.js`. The `test/` directory is deliberately not copied into the image.
- **`/healthz` is a real probe**: it reports database reachability and the age of the last moderation tick (three missed ticks = 503, with a startup grace period before the first one). Keep it cheap — the Docker healthcheck hits it every 30 s.
